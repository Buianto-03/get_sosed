# Архитектура фронтенда после перехода на FSD

Фронтенд организован вокруг пользовательских сценариев и бизнес-сущностей.
Модули размещаются в `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
Папки и публичные `index.ts` создаются только там, где они помогают отделить
ответственность. Количество строк в странице не является архитектурным правилом.

## Структура и границы

| Слой | Ответственность |
| --- | --- |
| `app` | провайдеры, store, маршруты и подключение чата к сессии |
| `pages` | полные представления маршрутов, собранные из виджетов, фич и сущностей |
| `widgets` | крупные части страниц: лента, профильные блоки, избранное, навигация и части чата |
| `features` | действия пользователя: формы, фильтрация, удаление лайка, отправка сообщения |
| `entities` | данные и API сессии, объявления, лайка и чата |
| `shared` | HTTP-клиент, конфигурация окружения и UI без бизнес-зависимостей |

Импорты идут вниз по слоям: `app → pages → widgets → features → entities → shared`.
Слайсы одного слоя не импортируют соседние слайсы. Единственное инфраструктурное
исключение — типизированные React Redux хуки из `app/store/hooks`: UI-модули
импортируют их для доступа к store. `shared` не импортирует `app` даже как тип.
Это проверяет `npm run check:architecture`, который входит в `npm run lint`.

Составные ответы API проверяются в потребляющей фиче. Например, ответ
«лайкнутое объявление» объединяет схему объявления и поля лайка в
`features/liked-adverts/model.ts`. Для него нет импорта между соседними
`entities`. Схема объявления содержит только нужные поля автора, поэтому не
зависит от схемы сессии.

Чтение объявления использует единый состав связей: `user` (id/name/email),
`location`, `AdvertPhotos`, `tags` (id/name). Сервер упорядочивает фотографии
по id ASC одним пакетным запросом на выборку, без запроса деталей для каждой
карточки. Отсутствующие фотографии возвращаются как пустой массив.
Zod-схема фотографии нормализует адрес через `shared/config/media.ts`:
относительный путь разрешается от origin `VITE_API_URL` (без `/api`),
абсолютный HTTP(S)-адрес сохраняется, отсутствующий путь становится
`undefined`. Этот же разбор применяется к вложенному объявлению избранного.
Nullable-поля отражают существующие миграции; отсутствие координат скрывает
карту, отсутствие ID автора блокирует переход к диалогу.


## Каталог условий проживания

`entities/advert/model/tag-catalog.ts` задаёт `ListingCondition` и состояния
`TagCatalogState` обычными enum. Названия основных условий сопоставляются
точно; ID берутся из ответа `GET /api/adverts/tags?query=`. Каталог сохраняет
также остальные теги, нужные произвольному поиску. Отсутствующие или
дублирующиеся основные названия считаются ошибкой каталога.

`useTagCatalog` загружает каталог через существующий advertService, предоставляет
retry и игнорирует поздний ответ после retry/размонтирования. Он подключён к
текущему Filter. Новые SearchFilters и ListingCreatePage принимают обязательный
`tagCatalog` через props; будущие route-контейнеры M15/M21 используют тот же
hook и передают результат вниз. Представления самостоятельно запросы не делают.
Preview передаёт собственный каталог из `preview/tag-catalog.ts`; рабочие
модули его не импортируют и при ошибке API демонстрационные ID не подставляют.

Выбранные ID текущего рабочего поиска уже находятся в URL. Строковые
conditions/rules незавершённых новых представлений переводятся на tagIds
в M15/M21; отправку выбранных ID публикации и сохранение AdvertTags обеспечивает
M22. M08 подготавливает каталог и props для этих задач. Старые UI-файлы
и неиспользуемый прежний helper вариантов публикации сохраняются до Q03.

## Принятые решения

- Роутер создаётся один раз. `ProtectedRoute` читает статус сессии сам;
  страницы загружаются по требованию через `React.lazy`.
- `shared/api/client.ts` получает доступ к токену и refresh через интерфейс,
  настроенный в `main.tsx`. При одновременных 403 используется один запрос
  refresh. После неудачного refresh сессия очищается.
- Применённые фильтры и идентификаторы тегов хранятся в URL. Локальное
  состояние формы содержит только черновик до применения. Запросы ленты
  запускаются при изменении URL; устаревший ответ не заменяет более новый.
- Одно WebSocket-соединение открывается для авторизованной сессии. Страницы
  выбирают диалог и отправляют сообщения через `entities/chat/model/socket.ts`.
  Соединение повторяется после обрыва и закрывается при выходе. Сервер
  возвращает `receiverId` с историей сообщений для правильной маршрутизации.
- Адрес WebSocket вычисляется из текущего сайта (`ws` или `wss`). В разработке
  Vite проксирует `/ws` на сервер. `VITE_WS_URL` и `VITE_API_URL` позволяют
  переопределить адреса.
- Вход, регистрация, публикация и редактирование профиля дожидаются результата
  запроса и показывают ошибку, если операция не завершилась успешно.

## Подготовка и перенос

Проверенные пункты исходного этапа 0: результат `liked.filter` присваивался,
`deleteLike` принимал id объявления, ключ Яндекса читался из переменной
окружения, маршрут `/post` был защищён, шаблон временных файлов Vite уже был
в `.gitignore`. Эти пункты не переносились как новые задачи. Дополнительно
исправлены подключение токена к HTTP-клиенту, обработка результатов форм и
проверка выбранных файлов при публикации.

Поиск объявлений перенесён первым рабочим срезом: фильтр, URL и лента имеют
разные обязанности. Затем перенесены формы, объявления, лайки, профиль и чат.
Старые технические папки `components`, `redux`, `services`, `types` больше не
содержат исходников. Удалены зависимости от `react-bootstrap`, `reactstrap`
и `bootstrap`; интерфейс использует Chakra UI.

RTK Query остаётся возможным отдельным проектом. Текущая миграция не меняет
механизм запросов ради одной только структуры каталогов.

## Планируемое подключение нового UI

Порядок дальнейшей работы описан в
[плане редизайна](../docs/redesign-migration-plan.md), обновлённом 16 октября
2026 года. Подготовленные компоненты пока работают в независимом preview;
переход основного приложения ещё не выполнен. Следующие положения задают
направление интеграции, а их фактическое выполнение отмечается в задачах плана.

- Сначала подключаются новые экраны к существующим сессии, API, Redux и
  WebSocket; затем проводится общая визуальная проверка и проверка доступности.
- Чистые константы браузерных адресов и builders размещаются в
  `shared/config/routes.ts`; конфигурация роутера и guards остаются в `app`.
  Прежний UI не опубликован в production; старые браузерные адреса удаляются
  без redirects и aliases. Новые переходы сохраняют нужные query/hash.
- Route-компоненты в `pages` связывают URL, данные и действия с готовыми
  представлениями. Компоненты отображения не импортируют preview fixtures.
  Контейнер и представление одного экрана находятся в одном слайсе страниц.
- Безопасная проверка `returnTo` — чистая функция в
  `shared/lib/navigation/safe-return-to.ts`. Она разрешает только локальный
  адрес и запрещает циклы на формы входа/регистрации. ProtectedRoute и обе
  auth-формы используют одну функцию выбора назначения после авторизации.
- До отдельного обоснованного объединения `entities/advert` хранит существующие
  API/модели, а `entities/listing` — подготовленный UI. Они не импортируют друг
  друга. Преобразования DTO в props выполняются в потребляющем верхнем слое.
- Общие стили, шрифт и CSS-переменные переносятся из preview в `shared/styles`
  и подключаются обоими entrypoints. Рабочие компоненты не зависят от размеров
  демонстрационной рамки; контейнерные запросы получают предка в SiteLayout.
- Сетевые изменения ограничены контрактами реальных сценариев: регистрацией
  без фото, сохранением профиля/тегов/фотографий, собственными объявлениями и
  чтением собеседника. Новые поля БД добавляются миграциями с сохранением данных.

До завершения интеграции Chakra остаётся у старых потребителей. Её удаление
проверяется после замены экранов; наличие нового UI в preview само по себе
не означает завершённый переход приложения.

Рабочий router подключает `app/layouts/app-layout/AppLayout.tsx`, который
собирает новый `SiteLayout`, сессию, шапку, футер и адаптивную мобильную
навигацию. Временно заменяемые старые страницы остаются источниками логики до
их экранных задач; недоступные ещё маршруты скрыты из новой навигации.

Старые UI-файлы сохраняются до Q03 как источник бизнес-логики. Перед заменой
экрана исполнитель изучает запросы, валидацию, обработку файлов, состояние и
действия в прежней реализации и записывает в журнал их новое расположение
и проверку. Новый UI получает отдельные контейнеры; отключение старого
компонента от маршрута не служит достаточным основанием удалить его файл.
Итог редизайна — полная замена оформления и удаление старых UI-файлов после
подтверждения переноса логики, с сохранением нужных API, моделей и thunks.

## Проверка изменений

Для каждого последующего PR запускать в `client/`:

```sh
npm run build
npm run lint
npm run test
```

Автоматические проверки покрывают состояние авторизации, повтор HTTP-запроса
после refresh, сериализацию фильтров в URL, лайки, защиту ленты от устаревших
ответов и адресацию истории чата.

Перед выпуском вручную пройти следующие сценарии на запущенном сервере и БД:

- регистрация, вход, выход и восстановление сессии после перезагрузки;
- прямая ссылка на `/home` с фильтрами и тегами, применение фильтра и кнопка
  «Назад» браузера;
- публикация с фото и ошибка публикации;
- просмотр объявления, лайк и удаление из избранного;
- редактирование профиля с фото;
- чат между двумя пользователями, переключение диалогов и восстановление
  соединения после обрыва.

Цель структуры — уменьшить связность и число конфликтующих источников
состояния. Само соответствие шаблону папок не является критерием готовности.
