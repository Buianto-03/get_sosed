# Архитектура фронтенда после перехода на FSD

Фронтенд организован вокруг пользовательских сценариев и бизнес-сущностей.
Модули размещаются в `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
Папки и публичные `index.ts` создаются только там, где они помогают отделить
ответственность. Количество строк в странице не является архитектурным правилом.

## Структура и границы

| Слой | Ответственность |
| --- | --- |
| `app` | провайдеры, store, маршруты и подключение чата к сессии |
| `pages` | полные представления маршрутов, собранные из виджетов, фич и сущностей |
| `widgets` | крупные части страниц: лента, профильные блоки, избранное, навигация и части чата |
| `features` | действия пользователя: формы, фильтрация, удаление лайка, отправка сообщения |
| `entities` | данные и API сессии, объявления, лайка и чата |
| `shared` | HTTP-клиент, конфигурация окружения и UI без бизнес-зависимостей |

Импорты идут вниз по слоям: `app → pages → widgets → features → entities → shared`.
Слайсы одного слоя не импортируют соседние слайсы. Единственное инфраструктурное
исключение — типизированные React Redux хуки из `app/store/hooks`: UI-модули
импортируют их для доступа к store. `shared` не импортирует `app` даже как тип.
Это проверяет `npm run check:architecture`, который входит в `npm run lint`.

Контракт избранного объявления расположен в
`entities/advert/model/likedAdvertsModel.ts`: это полное объявление и идентификаторы
связи сохранения. Он использует схему объявления своего слайса и не импортирует
`entities/like`. Схема объявления содержит только нужные поля автора, поэтому
не зависит от схемы сессии.

Чтение объявления использует единый состав связей: `user` (id/name/email),
`location`, `AdvertPhotos`, `tags` (id/name). Сервер упорядочивает фотографии
по id ASC одним пакетным запросом на выборку, без запроса деталей для каждой
карточки. Отсутствующие фотографии возвращаются как пустой массив.
Zod-схема фотографии нормализует адрес через `shared/config/media.ts`:
относительный путь разрешается от origin `VITE_API_URL` (без `/api`),
абсолютный HTTP(S)-адрес сохраняется, отсутствующий путь становится
`undefined`. Этот же разбор применяется к вложенному объявлению избранного.
Nullable-поля отражают существующие миграции; отсутствие координат скрывает
карту, отсутствие ID автора блокирует переход к диалогу.

## Каталог условий проживания

`entities/advert/model/tag-catalog.ts` задаёт `ListingCondition` и состояния
`TagCatalogState` обычными enum. Названия основных условий сопоставляются
точно; ID берутся из ответа `GET /api/adverts/tags?query=`. Каталог сохраняет
также остальные теги, нужные произвольному поиску. Отсутствующие основные названия и повтор одного ID считаются ошибкой каталога.
Одинаковые названия с разными ID сохраняются: быстрые условия выбирают
минимальный ID, остальные доступны в дополнительных фильтрах с подписью (#ID).
Существующие URL и связи не переписываются и не удаляются.

`useTagCatalog` загружает каталог через существующий advertService, предоставляет
retry и игнорирует поздний ответ после retry/размонтирования. Route-контейнеры используют его для
каталога условий. SearchFilters и ListingCreatePage принимают обязательный
`tagCatalog` через props; route-контейнеры поиска и публикации используют тот же
hook и передают результат вниз. Представления самостоятельно запросы не делают.
При ошибке API демонстрационные ID не подставляются.

Выбранные ID находятся в URL поиска и в tagIds черновика публикации. Labels
вычисляются из каталога при отображении; IDs неизвестных URL сохраняются
с fallback #ID. SearchFilters/FilterForm хранят только draft и показывают все
границы цены/комнат и произвольные теги. Применение меняет query, Back/Forward
обновляют draft; ввод не запускает выдачу. Каталог при ошибке не очищает URL.
Публикация отправляет JSON tagIds; сервер валидирует ID и сохраняет AdvertTags.
Старый Filter удалён в Q03 после сверки переноса URL, draft и выбора тегов.

## Файлы Redux-модели сущности

Для каждого Redux-состояния в `entities` slice, thunk, model и selectors находятся в
разных файлах с одним префиксом и точными суффиксами:

- `{name}Slice.ts`: createSlice, initialState, reducers и actions.
- `{name}Thunk.ts`: асинхронные thunks и выполнение запросов.
- `{name}Model.ts`: интерфейсы/типы состояния и payload, enum и схемы валидации.
- `{name}Selectors.ts`: чтение состояния и вычисление производных значений.

Например, избранное использует `likedAdvertsSlice.ts`, `likedAdvertsThunk.ts`
`likedAdvertsModel.ts` и `likedAdvertsSelectors.ts` в `entities/advert/model/`. Суффикс файла `Thunk`
остаётся в единственном числе при нескольких экспортируемых thunks.
Model не импортирует Slice/Thunk; Thunk зависит от Model и API,
Slice — от Model и lifecycle actions из Thunk. Selectors зависит только от
типов Model. Объявления моделей, thunks и селекторов не размещаются внутри
файла Slice. Направление импортов FSD сохраняется.

## Общее избранное

`entities/advert/model/likedAdvertsSlice.ts` хранит список карточек, savedIds, статус
загрузки, общую ошибку и pending/errors по ID объявления. Это единственный
источник признака сохранения для поиска, популярных карточек, деталей и
профиля. `likes.likes` содержит заинтересованных в открытом объявлении;
его нельзя использовать как список избранного текущего пользователя.

Избранное — коллекция объявлений, поэтому его состояние, контракт ответа,
селекторы и загрузка находятся в существующем слайсе `entities/advert`.
`likedAdvertsSelectors.ts` содержит селекторы,
`likedAdvertsThunk.ts` — загрузку; контракт и типы находятся в
`likedAdvertsModel.ts`. `advertService.getLikedAdverts` разбирает GET `/adverts/liked` общей схемой
объявления. Это позволяет обойтись без отдельной сущности и копии Advert DTO.

`features/liked-adverts/model.ts` содержит только сценарии сохранения и
удаления: вызывает thunks `entities/like` и отправляет события начала,
подтверждения или ошибки в `entities/advert`. Reducer принимает подтверждение
по действующему requestId. Feature-hook связывает это действие с сессией и
навигацией гостя. Между соседними entities нет импортов.

`store.ts` использует обычный объект reducers в configureStore.
`app/store/session-listener.ts` следит за изменением ID авторизованного
пользователя: отправляет actions сброса обоих состояний без await, затем
загружает избранное после входа или восстановления сессии. Сброс завершается
до возврата auth dispatch; старые Promise-ответы не успевают примениться между
сменой пользователя и очисткой requestId. Обновление auth и сбросы — отдельные
actions, поэтому подписчики store могут увидеть промежуточное состояние.
Повторная установка токена того же пользователя
не очищает список. Reducers принимают ответы только с действующим requestId,
включая ответы мутаций; старый запрос не заполняет следующую сессию.

Страницы и виджеты используют селекторы, saveAdvertThunk/removeSavedAdvertThunk
и `useSavedAdverts`. Hook отправляет гостя на вход с текущими pathname,
search и hash в returnTo. Новые представления получают saved/pending/callback
через props при своих экранных задачах. Текущие рабочие карточки уже используют
общий источник. Изменения подтверждаются только после ответа; повторная
мутация одного ID блокируется. Загрузка полного списка и мутации исключают
друг друга, чтобы снимок списка не затёр подтверждённое изменение.

Сохранение принимает полный DTO объявления и обновляет профильную карточку
без дополнительного запроса деталей. Ошибка сохраняет прежние карточки и
сердечко. DELETE разбирается отдельной схемой `{ advertId, deleted }`;
`deleted: false` также подтверждает отсутствие лайка. В списке заинтересованных
удаляется лайк текущего пользователя по advertId, лайки остальных сохраняются.
Интеграционные тесты с настоящим store находятся в app/store, чтобы не
нарушать направление импортов FSD.

## Принятые решения

- Роутер создаётся один раз. `ProtectedRoute` читает статус сессии сам;
  страницы загружаются по требованию через `React.lazy`.
- `shared/api/client.ts` получает доступ к токену и refresh через интерфейс,
  настроенный в `main.tsx`. При одновременных 403 используется один запрос
  refresh. После неудачного refresh сессия очищается.
- Применённые фильтры и идентификаторы тегов хранятся в URL. Локальное
  состояние формы содержит только черновик до применения. Запросы ленты
  запускаются при изменении URL; устаревший ответ не заменяет более новый.
- Одно WebSocket-соединение открывается для авторизованной сессии. Страницы
  выбирают диалог и отправляют сообщения через `entities/chat/model/socket.ts`.
  Соединение повторяется после обрыва и закрывается при выходе. Сервер
  возвращает `receiverId` с историей сообщений для правильной маршрутизации.
- Адрес WebSocket вычисляется из текущего сайта (`ws` или `wss`). В разработке
  Vite проксирует `/ws` на сервер. `VITE_WS_URL` и `VITE_API_URL` позволяют
  переопределить адреса.
- Вход, регистрация, публикация и редактирование профиля дожидаются результата
  запроса и показывают ошибку, если операция не завершилась успешно.

## Подготовка и перенос

Проверенные пункты исходного этапа 0: результат `liked.filter` присваивался,
`deleteLike` принимал id объявления, ключ Яндекса читался из переменной
окружения, маршрут `/post` был защищён, шаблон временных файлов Vite уже был
в `.gitignore`. Эти пункты не переносились как новые задачи. Дополнительно
исправлены подключение токена к HTTP-клиенту, обработка результатов форм и
проверка выбранных файлов при публикации.

Поиск объявлений перенесён первым рабочим срезом: фильтр, URL и лента имеют
разные обязанности. Затем перенесены формы, объявления, лайки, профиль и чат.
Старые технические папки `components`, `redux`, `services`, `types` больше не
содержат исходников. Удалены зависимости от `react-bootstrap`, `reactstrap`
и `bootstrap`. Рабочие экраны используют собственный UI kit. В Q03 удалены
старые страницы, формы и виджеты, ChakraProvider и пакеты Chakra/Emotion,
Framer Motion и react-slick. API, Redux, thunks и используемые helpers сохранены.

RTK Query остаётся возможным отдельным проектом. Текущая миграция не меняет
механизм запросов ради одной только структуры каталогов.

## Подключение нового UI

Порядок дальнейшей работы описан в
[плане редизайна](../docs/redesign-migration-plan.md). M01–M28 завершены;
Q01 выполнена 1 ноября 2026 года, результаты — в
[визуальной приёмке](../docs/redesign-visual-qa.md). Очистка Q03 выполнена
2 ноября; общая приёмка Q02 остаётся открытой до физического телефона
и скринридера. Реестр удаления и исключения — раздел 27 журнала интеграции.
Следующие положения описывают разделение ответственности подключённых экранов.

- Сначала подключаются новые экраны к существующим сессии, API, Redux и
  WebSocket; затем проводится общая визуальная проверка и проверка доступности.
- Чистые константы браузерных адресов и builders размещаются в
  `shared/config/routes.ts`; конфигурация роутера и guards остаются в `app`.
  Прежний UI не опубликован в production; старые браузерные адреса удаляются
  без redirects и aliases. Новые переходы сохраняют нужные query/hash.
- Route-компоненты в `pages` связывают URL, данные и действия с готовыми
  представлениями. Компоненты отображения получают данные через props.
  Контейнер и представление одного экрана находятся в одном слайсе страниц.
- Повторяемый переход к публикации инкапсулирован в
  `features/listing-create/ui/create-listing-button/CreateListingButton.tsx`.
  Баннер и профиль используют компонент на основе общего `Button` без передачи
  `onCreateListing` из route-компонентов. Кнопка вызывает `useNavigate` внутри;
  проверка сессии и возврат после входа остаются в `ProtectedRoute`.
  Пустое состояние коллекции профиля принимает готовый элемент `action`.
- Безопасная проверка `returnTo` — чистая функция в
  `shared/lib/navigation/safe-return-to.ts`. Она разрешает только локальный
  адрес и запрещает циклы на формы входа/регистрации. ProtectedRoute и обе
  auth-формы используют одну функцию выбора назначения после авторизации.
- До отдельного обоснованного объединения `entities/advert` хранит существующие
  API/модели, а `entities/listing` — подготовленный UI. Они не импортируют друг
  друга. Преобразования DTO в props выполняются в потребляющем верхнем слое.
- Общие стили, шрифт и CSS-переменные находятся в `shared/styles`
  и подключаются в `main.tsx`. Контейнерные запросы рабочих компонентов
  получают предка в SiteLayout.
- Сетевые изменения ограничены контрактами реальных сценариев: регистрацией
  без фото, сохранением профиля/тегов/фотографий, собственными объявлениями и
  чтением собеседника. Новые поля БД добавляются миграциями с сохранением данных.

Общие foundations задают CSS-переменные, локальный Inter и базовый reset
в `shared/styles/foundations.scss`. Рабочий entrypoint импортирует их
напрямую. Провайдер стилей
и приватные адаптеры Chakra не нужны. Единственный библиотечный UI-адаптер —
`shared/ui/y-map`: он оборачивает SDK Яндекс.Карт и владеет его состояниями.

Рабочий router подключает `app/layouts/app-layout/AppLayout.tsx`, который
собирает новый `SiteLayout`, сессию, шапку, футер и адаптивную мобильную
навигацию. Все рабочие маршруты подключены; старые страницы удалены
после сверки переноса в Q03. Гостю доступны ссылки нижней навигации,
а допуск к защищённому маршруту проверяет ProtectedRoute.

`app/layouts/site-layout/SiteLayout.tsx` отвечает за композицию оболочки.
`SiteContent` владеет контейнером содержимого, его адаптивными стилями и
`useRouteContentFocus`: при смене pathname фокус переносится на h1, при
асинхронной загрузке hook дожидается заголовка. Изменение query не переносит
фокус. `SkipLink` содержит ссылку пропуска шапки, её стили и переход фокуса
на main либо контейнер содержимого. Эти компоненты остаются в app/layouts;
сессия и действия пользователя по-прежнему подключаются в AppLayout.

Реестр переноса в журнале фиксирует новое расположение запросов, валидации,
обработки файлов и действий прежнего UI. В Q03 проверены потребители, включая lazy imports, и физически удалён прежний UI. Исторические
решения о сохранении исходников в ранних разделах журнала больше не действуют.
Отдельные сценарии старого оформления заменены осознанно: популярная подборка —
свежими объявлениями, модальное подтверждение удаления лайка — обратимым
переключателем, встроенный список чатов профиля — маршрутом `/messages`.
API, модели, store и thunks остаются источниками бизнес-состояния.

## Проверка изменений

Для каждого последующего PR запускать в `client/`:

```sh
npm run build
npm run lint
npm run test
```

Автоматические проверки покрывают состояние авторизации, повтор HTTP-запроса
после refresh, сериализацию фильтров в URL, лайки, защиту ленты от устаревших
ответов и адресацию истории чата.

Перед выпуском вручную пройти следующие сценарии на запущенном сервере и БД:

- регистрация, вход, выход и восстановление сессии после перезагрузки;
- прямая ссылка на `/listings` с фильтрами и тегами, применение фильтра и кнопка
  «Назад» браузера;
- публикация с фото и ошибка публикации;
- просмотр объявления, лайк и удаление из избранного;
- редактирование профиля с фото;
- чат между двумя пользователями, переключение диалогов и восстановление
  соединения после обрыва.

Цель структуры — уменьшить связность и число конфликтующих источников
состояния. Само соответствие шаблону папок не является критерием готовности.

## Подключённые страницы авторизации, главной и About

Рабочие маршруты `/sign-in` и `/sign-up` используют отдельные route-компоненты
в существующих page-слайсах. Контейнеры `features/sign-in/ui/sign-in-form`
и `features/sign-up/ui/sign-up-form` владеют значениями, валидацией,
loading/error и отправкой через прежние thunks. SignInCard/SignUpCard остаются
управляемыми представлениями. Signup thunk преобразует 409/EMAIL_ALREADY_EXISTS
в различимую ошибку поля; API service сохраняет исходную ошибку. Навигация
использует общий safe-return-to, подтверждение пароля не уходит на сервер.
Правило имён Redux-файлов выше относится только к entities.

Главная `pages/welcome/ui/home-route` читает advertService в локальное состояние,
сортирует объявления по createdAt DESC и берёт три. Состояние поисковой выдачи
не используется для этой подборки и не меняется. Effect игнорирует поздний ответ
после cleanup; helper страницы преобразует Advert DTO в ListingCardData.
Избранное и его pending/errors приходят из общего M09 hook через props
FreshListings/ListingCard. Нулевая цена и отсутствующая цена различаются.
Рабочие страницы используют данные API. AboutPage использует только
готовые виджеты и реальные callbacks навигации. Старые page/form-файлы
удалены после сверки переноса в Q03.

## Все рабочие экраны подключены

Router использует SearchRoute, ListingRoute, ProfileRoute, ProfileEditRoute,
ListingCreateRoute и MessagesRoute вместе с уже подключёнными главной,
авторизацией и About. Старые page/form-файлы удалены в Q03. Статические маршруты остаются enum, динамические
URL собираются шаблонными строками в builders.

Redux-модули, изменённые интеграцией, приведены к соглашению файлов:
`advertsModel/advertsThunk/advertsSlice/advertsSelectors`,
`chatListModel/chatListThunk/chatListSlice/chatListSelectors`,
`authModel/authThunk/authSlice`. Это не правило для feature/model.ts.

Поиск и детали имеют независимые статусы/requestId в состоянии advert.
Новый detail request очищает chosenAdvert; поздние success/error игнорируются.
Pagination — по 8 карточек, счётчик показывает полное количество. Преобразования
Advert DTO в UI остаются в helper потребляющей страницы. Кнопка возврата деталей
принимает только безопасный локальный /listings с query, иначе /listings.
Карта и заинтересованные передаются в ListingInformation слотами; YMap нового
адаптера не зависит от Chakra. Карта недоступна без ключа/координат.

Профиль читает сессию, /adverts/mine и общее избранное с независимыми статусами.
Свои объявления загружаются по 12 через `GET /api/adverts/mine?page=1&limit=12`.
Ответ `{ items, total, page, limit }` разбирается `advertPageSchema`; `total`
задаёт счётчик коллекции. Кнопка «Показать ещё» добавляет следующую страницу
без повторов по ID. `useMyAdverts` в profile-route хранит локальную коллекцию,
отдельные состояния первой загрузки и догрузки, блокирует параллельные запросы
и игнорирует ответы прежнего владельца/размонтированного экрана. При ошибке
догрузки карточки сохраняются, повтор запрашивает ту же страницу. Наличие
следующей страницы определяется по `page * limit < total`, а не по длине
объединённого списка после удаления повторов.
Редактирование отправляет FormData и устанавливает пользователя из ответа
через updateUser, сохраняя accessToken. UserProfile допускает null; city/intent
nullable, habits массив. Фото не передано — сохранить; File — заменить;
removePhoto=true — удалить. Сервер проверяет владельца и allowlist, согласует
записи в транзакции и не возвращает hashpass.

Публикация хранит все поля и 1–10 фото в черновике, повторно проверяет все шаги
перед отправкой. Builder явно переводит area→square, description→body,
tagIds→JSON и ставит главный File первым. Геокодирование опционально: ошибка
не создаёт фиктивных координат. Сервер проверяет декодирование фото/ID тегов,
сохраняет связанные записи в транзакции и ждёт всех файлов до 201.

MessagesRoute используется и для индекса, и для выбранного receiverId.
Список загружается защищённым GET /users/:currentId, новый собеседник — отдельным
GET /users/:receiverId/summary. Опциональный listingId проверяется по автору.
В state истории разделены по ID; live events и history объединяются по message.id.
`app/hooks/useChatConnection.ts`, вызываемый из App, управляет одним socket
на сессию и связывает события с Redux. Старый socket не вызывает нового listener;
смена владельца синхронно очищает chat state. Reconnect восстанавливает активную
историю. Серверные события обновляют последнюю строку списка, включая новый диалог.
Сервер сохраняет сообщение для offline-получателя и рассылает всем вкладкам
участников только безопасные поля. sendMessage=true подтверждает передачу в
socket; подтверждения сохранения/delivery ticks протокол не предоставляет.

Production build очищает generated server/dist (emptyOutDir), поэтому старые
chunks не накапливаются. Express отдаёт SPA для браузерных маршрутов; неизвестные
/api и /images получают 404, обычный HTTP /ws — 426, upgrade принимается только
для /ws. Обобщённого Yandex proxy на неизвестные API-адреса больше нет;
карта/геокодер используют собственные официальные адреса SDK/API.

## Компоновка Q01

SiteLayout ограничивает chat-layout высотой 100dvh. Route-контейнер по-прежнему
владеет API/session/socket, а ChatPage — отображением, черновиком и положением
прокрутки истории. История имеет собственный overflow, composer остаётся в
панели; ResizeObserver сохраняет нижнюю позицию при изменении размеров, если
пользователь не перешёл к чтению старых сообщений. Низкий мобильный viewport
использует компактный контекст без быстрых фраз. Протокол отправки не изменён.

Статические изображения оболочки лежат в корне public,
так как /images в development направлен на API.
