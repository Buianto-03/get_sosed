# Архитектура фронтенда после перехода на FSD

Фронтенд организован вокруг пользовательских сценариев и бизнес-сущностей.
Модули размещаются в `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
Папки и публичные `index.ts` создаются только там, где они помогают отделить
ответственность. Количество строк в странице не является архитектурным правилом.

## Структура и границы

| Слой | Ответственность |
| --- | --- |
| `app` | провайдеры, store, маршруты и подключение чата к сессии |
| `pages` | полные представления маршрутов, собранные из виджетов, фич и сущностей |
| `widgets` | крупные части страниц: лента, профильные блоки, избранное, навигация и части чата |
| `features` | действия пользователя: формы, фильтрация, удаление лайка, отправка сообщения |
| `entities` | данные и API сессии, объявления, лайка и чата |
| `shared` | HTTP-клиент, конфигурация окружения и UI без бизнес-зависимостей |

Импорты идут вниз по слоям: `app → pages → widgets → features → entities → shared`.
Слайсы одного слоя не импортируют соседние слайсы. Единственное инфраструктурное
исключение — типизированные React Redux хуки из `app/store/hooks`: UI-модули
импортируют их для доступа к store. `shared` не импортирует `app` даже как тип.
Это проверяет `npm run check:architecture`, который входит в `npm run lint`.

Составные ответы API проверяются в потребляющей фиче. Например, ответ
«лайкнутое объявление» объединяет схему объявления и поля лайка в
`features/liked-adverts/model.ts`. Для него нет импорта между соседними
`entities`. Схема объявления содержит только нужные поля автора, поэтому не
зависит от схемы сессии.

## Принятые решения

- Роутер создаётся один раз. `ProtectedRoute` читает статус сессии сам;
  страницы загружаются по требованию через `React.lazy`.
- `shared/api/client.ts` получает доступ к токену и refresh через интерфейс,
  настроенный в `main.tsx`. При одновременных 403 используется один запрос
  refresh. После неудачного refresh сессия очищается.
- Применённые фильтры и идентификаторы тегов хранятся в URL. Локальное
  состояние формы содержит только черновик до применения. Запросы ленты
  запускаются при изменении URL; устаревший ответ не заменяет более новый.
- Одно WebSocket-соединение открывается для авторизованной сессии. Страницы
  выбирают диалог и отправляют сообщения через `entities/chat/model/socket.ts`.
  Соединение повторяется после обрыва и закрывается при выходе. Сервер
  возвращает `receiverId` с историей сообщений для правильной маршрутизации.
- Адрес WebSocket вычисляется из текущего сайта (`ws` или `wss`). В разработке
  Vite проксирует `/ws` на сервер. `VITE_WS_URL` и `VITE_API_URL` позволяют
  переопределить адреса.
- Вход, регистрация, публикация и редактирование профиля дожидаются результата
  запроса и показывают ошибку, если операция не завершилась успешно.

## Подготовка и перенос

Проверенные пункты исходного этапа 0: результат `liked.filter` присваивался,
`deleteLike` принимал id объявления, ключ Яндекса читался из переменной
окружения, маршрут `/post` был защищён, шаблон временных файлов Vite уже был
в `.gitignore`. Эти пункты не переносились как новые задачи. Дополнительно
исправлены подключение токена к HTTP-клиенту, обработка результатов форм и
проверка выбранных файлов при публикации.

Поиск объявлений перенесён первым рабочим срезом: фильтр, URL и лента имеют
разные обязанности. Затем перенесены формы, объявления, лайки, профиль и чат.
Старые технические папки `components`, `redux`, `services`, `types` больше не
содержат исходников. Удалены зависимости от `react-bootstrap`, `reactstrap`
и `bootstrap`; интерфейс использует Chakra UI.

RTK Query остаётся возможным отдельным проектом. Текущая миграция не меняет
механизм запросов ради одной только структуры каталогов.

## Проверка изменений

Для каждого последующего PR запускать в `client/`:

```sh
npm run build
npm run lint
npm run test
```

Автоматические проверки покрывают состояние авторизации, повтор HTTP-запроса
после refresh, сериализацию фильтров в URL, лайки, защиту ленты от устаревших
ответов и адресацию истории чата.

Перед выпуском вручную пройти следующие сценарии на запущенном сервере и БД:

- регистрация, вход, выход и восстановление сессии после перезагрузки;
- прямая ссылка на `/home` с фильтрами и тегами, применение фильтра и кнопка
  «Назад» браузера;
- публикация с фото и ошибка публикации;
- просмотр объявления, лайк и удаление из избранного;
- редактирование профиля с фото;
- чат между двумя пользователями, переключение диалогов и восстановление
  соединения после обрыва.

Цель структуры — уменьшить связность и число конфликтующих источников
состояния. Само соответствие шаблону папок не является критерием готовности.
