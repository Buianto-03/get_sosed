# GETSOSED: переход рабочего приложения на новый UI

Обновлено: 18 октября 2026 года. Цель — полностью заменить прежний дизайн новым, подключить подготовленные экраны к маршрутам, сессии, API и WebSocket, сохранить необходимую бизнес-логику и после интеграции провести итоговую проверку. По уточнению пользователя прежний UI не опубликован в production, поэтому поддержка старых браузерных адресов и перенаправления с них не требуются. Старые UI-файлы сохраняются до переноса и проверки их бизнес-логики; окончательное удаление выполняется в Q03.

**M01–M28 выполнены: все рабочие маршруты подключены к новому UI.** M08/M11 дополнительно проверены на живой development-БД, миграции применены. Сценарии API/БД/WebSocket, браузерная публикация и production SPA fallback проверены; результаты и ограничения — в [журнале](redesign-integration-progress.md), раздел 18. Следующий этап — Q01 (итоговая визуальная сверка), затем Q02 и Q03. Старые исходные UI-файлы сохранены для сверки бизнес-логики до Q03.

### Что должно получиться

- Основной `index.html` открывает новый UI всех пользовательских экранов.
- Регистрация, вход, выход, восстановление сессии, фильтрация, избранное, профиль, публикация и чат работают с сервером.

- Итоговые Q01 и Q02 проверяют основное приложение; preview используется для трудновоспроизводимых визуальных состояний.

### Границы работ

Переиспользовать текущие Redux slices, thunks, Axios-клиент, refresh и `chatSocket`. Не вводить RTK Query, другой роутер или новый механизм авторизации ради редизайна. Сервер менять точечно там, где новый UI требует реального сохранения данных или текущий контракт не позволяет завершить сценарий. Такие изменения перечислены ниже.

Не добавлять каталог соседей, новый протокол диалогов по объявлениям, постоянное хранение черновика публикации или другие самостоятельные продуктовые функции. Названия браузерных маршрутов можно изменить; существующие `/api/adverts`, `/api/users`, `/api/likes` и WebSocket-протокол не переименовывать вслед за ними.

## 2. Правила выполнения одной задачи

Пути `app/...`, `pages/...`, `widgets/...`, `features/...`, `entities/...`, `shared/...` и `preview/...` в карточках отсчитываются от `client/src/`; пути с `client/`, `server/` и `docs/` — от корня репозитория. Названия новых файлов и маршрутов в плане задают целевое состояние, а не утверждают, что они уже существуют.

1. Прочитать `AGENTS.md`, `client/ARCH.md`, этот раздел и карточку выбранной задачи. Проверить `git status`; сохранить чужие изменения.
2. Проверить результат перечисленных зависимостей. Если задача уже частично реализована, дополнить её, не создавать второй механизм.
3. Менять только указанный сценарий и непосредственно необходимые общие контракты. Новые React-компоненты размещать со своим SCSS Module в отдельной kebab-case папке, props объявлять через `interface`, компонентные helpers — в соседнем `helper.ts`.
4. Импорты внутри слайса — относительные, между слоями/слайсами — через aliases. Соблюдать FSD; не добавлять исключения в проверку границ ради обхода ошибки.
5. После изменения сценария выполнить локальную проверку desktop/mobile и ошибок именно этого сценария. Полная матрица всех экранов выполняется после интеграции в Q01.
6. Для изменений клиентского кода выполнить в `client/`: `npm test`, `npm run lint`, `npm run build`. Добавлять тесты для значимого нового поведения; не тестировать CSS-значения и повторы реализации.
7. Для серверных изменений выполнить адресные API/БД-проверки из карточки. `npm test` в `server/` — заглушка и не является проверкой. Секреты не записывать в отчёт. Не запускать `npm run db`: команда удаляет БД. Новые миграции применять из `server/` через установленный `sequelize-cli db:migrate` на настроенной development/test БД; старые данные и миграции сохранять.
8. Обновить строку задачи и [журнал интеграции](redesign-integration-progress.md): что изменено, какие проверки прошли, какие не выполнены и почему. Код, не проверенный из-за отсутствия сервера/БД, так и обозначать; не выдавать его за принятый end-to-end сценарий.

Статусы: `TODO` — не начата; `WIP` — выполняется; `DONE` — выполнены критерии карточки; `BLOCKED` — конкретная внешняя зависимость мешает завершению. Ограничение доступа к дизайну не блокирует всю интеграцию; оно оставляет открытой соответствующую визуальную приёмку Q01.

### Сохранение старых файлов до переноса логики

Старые компоненты могут содержать запросы, валидацию, обработку файлов, преобразование данных, правила доступа и навигацию. Не удалять эти файлы сразу после появления нового представления и не переписывать их целиком, теряя источник логики.

1. Перед переносом сценария прочитать его старую страницу, связанные widgets/features и вызываемые services/thunks.
2. В журнале записать: исходный файл/функция → назначение → новый файл/функция → проверка переноса. Неиспользуемую логику отметить с причиной отказа; не считать её перенесённой только из-за отсутствия импортов.
3. Переиспользовать существующие модели/thunks/services; логику из UI перенести в новый контейнер, helper или feature по FSD. Не копировать старую разметку и не создавать два действующих источника состояния.
4. Новые контейнеры создавать в новых файлах. Старые UI-файлы оставить доступными для сверки до Q03; минимальные исправления их типов/импортов при изменении общих контрактов допустимы.
5. После подключения нового экрана отключить старый компонент от рабочего маршрута. Физическое наличие исходного файла не означает сохранение отдельного старого маршрута или старого дизайна в результате.
6. В Q03 удалять файлы по реестру только после проверки переноса логики, прохождения сценария и отсутствия потребителей. Бизнес-модели, API, store и перенесённые helpers не удалять только из-за их прежнего расположения.

### Разделение данных и отображения

- Route-компонент в `pages` читает URL/store, загружает данные, собирает представление и передаёт обработчики. Представления и UI kit не импортируют preview fixtures.
- Транспорт и схемы ответов остаются в существующей `entities/advert`; UI объявления пока остаётся в `entities/listing`. Не переименовывать оба слайса одновременно с интеграцией.
- `entities/advert` не импортирует соседний `entities/listing`. Преобразование `AdvertType` в props `ListingCard`/`ListingDetails` размещать в helper потребляющей страницы; не переносить API DTO в `shared` ради обхода границ.
- Формы входа и регистрации используют thunks своего feature. Страница публикации может импортировать feature `listing-create` и thunk из `create-advert`; feature `listing-create` не импортирует соседнюю feature.
- Route-компонент и готовый экран одного слайса имеют разные имена, например `ProfileRoute` и `ProfilePage`, `MessagesRoute` и `ChatPage`. Страница не импортирует другую страницу для повторного использования UI.
- Перечни городов/метро из preview не являются справочниками backend. До появления настоящего справочника использовать ввод текстом; не отправлять московские станции для другого города.

## 3. Целевые браузерные маршруты

| Назначение | Адрес | Доступ |
| --- | --- | --- |
| Главная | `/` | Любой |
| Поиск | `/listings` | Любой |
| Объявление | `/listings/:listingId` | Любой |
| Публикация | `/listings/new` | Авторизованный |
| О сервисе | `/about` | Любой |
| Вход | `/sign-in` | Гость |
| Регистрация | `/sign-up` | Гость |
| Профиль | `/profile` | Авторизованный |
| Редактирование | `/profile/edit` | Авторизованный |
| Список диалогов | `/messages` | Авторизованный |
| Переписка | `/messages/:receiverId` | Авторизованный |
| Неизвестный адрес | `*` — любой несовпавший путь | Любой |

Правила:

- Единственный источник строк и builders — чистый модуль `shared/config/routes.ts`. Предусмотреть `listingDetails(id)` и `messageThread(receiverId)`; в меню не должно быть `/messages/1` или `/listings/1`.
- Статический `/listings/new` должен распознаваться как публикация, а не как идентификатор объявления. ID — положительные целые числа; неверные ID показывают понятную ошибку без запроса `NaN` к API.
- Старые `/home`, `/advert/:id`, `/post`, `/account`, `/chat/:receiverId`, `/signin`, `/signup` удаляются из router без redirects и aliases. Для них, как и для любого неизвестного адреса, показывается NotFoundPage с сохранением введённого URL.
- В M02 можно временно подключить существующие страницы к новым адресам на период разработки. Это промежуточное состояние до подключения нового представления в задаче соответствующего сценария. При переименовании `:id` в `:listingId` одновременно обновить чтение параметра в старом AdvertPage; исходную бизнес-логику сохранить для M17. К M28 все эти временные UI-подключения должны быть заменены новым дизайном.
- Маршруты без старого аналога подключаются вместе с реализацией соответствующей страницы. До этого не добавлять в меню ссылки на отсутствующие маршруты. Это касается `/about`, `/profile/edit` и индекса `/messages`.
- URL фильтров сохраняет существующие ключи: `city`, `district`, `metro`, `priceFrom`, `priceTo`, `roomsFrom`, `roomsTo`, `tags`. `tags` содержит реальные числовые ID, разделённые запятыми.
- Гость после защищённого действия попадает на `/sign-in?returnTo=...`. В `returnTo` записывается локальный адрес назначения вместе с его query/hash. После входа/регистрации возвращаться туда; без назначения — в `/profile`.
- Проверять `returnTo`: разрешён только адрес этого приложения, без внешнего origin, `//`, переходов обратно на формы авторизации и циклов редиректов. Не выполнять произвольный переход из query.
- На `/messages` ничего не выбирать автоматически. На телефоне возврат из переписки ведёт на список. Параметр `receiverId` — ID пользователя, не ID сообщения и не ID объявления.

### Точные преобразования запросов

Не переименовывать поля API вслед за названиями UI. Эти соглашения реализуются соответствующими задачами и записываются в журнал M01.

| Сценарий | Контракт |
| --- | --- |
| Регистрация | FormData: `name`, `email`, `password`; необязательные прежние `file` и `gender`. Ответ: `{ user, accessToken }`, как сейчас. |
| Профиль | PATCH FormData: `name`, `city`, `intent`, `about` (из UI description), `habits` как JSON-массив строк; прежние `age`/`phoneNumber` при редактировании. Пустые age/phoneNumber переводить в null на сервере, а не в 0. Ответ — объект пользователя с UserProfile, без обёртки и без токена. |
| Аватар | `avatarFile === undefined` — не отправлять фото и флаг; `File` — поле `photo`; `null` — `removePhoto=true`. Файл и флаг удаления одновременно недопустимы. Blob URL предпросмотра не отправляется. |
| Публикация | FormData: `title`, `body` из description, `price`, `rooms`, `floor`, `square` из area, `city`, `district`, `address`, `metro`; `tagIds` — JSON-массив числовых ID, даже для пустого списка `[]`; `files` — повторяющееся поле для File. Автор определяется сервером. |
| Координаты | Необязательное `coordinates` в существующем формате `широта, долгота`; без результата геокодирования поле не отправляется, хранится null. Не путать порядок координат в ответе геокодера. |
| Поиск | Существующий POST `/api/adverts/filters`: числовые границы, строки местоположения, `tags: [{ id, name: '' }]` из query tagIds. Строковые labels условий не отправляются вместо ID. |
| Диалог | `/messages/:receiverId` использует ID собеседника; отправка сохраняет существующий `ADD_MESSAGE` с `{ receiverId, text }`. Необязательный listingId хранится только в query контекста и не заменяет receiverId. |
| Повторные лайки после M09 | POST `/api/likes/:advertId`: новый Like с 201 или существующий с 200. DELETE того же адреса: 200 `{ advertId, deleted: boolean }` для найденной и отсутствующей записи. Клиентский parser/thunk/reducers меняются одновременно; до M09 ответы нестабильны. |

Новые client-side типы draft/props обязаны отражать эти соглашения. Если отправлено неизвестное поле, сервер не должен сообщать, что оно сохранено; принимаемые поля перечисляются явно в обработчике.

## 8. Как передавать отдельную задачу другой модели

Передавать один ID, этот план и актуальный журнал. Не просить модель самостоятельно выбрать архитектуру из нескольких вариантов: основные решения уже перечислены в разделах 2–4.

Шаблон задания:

> Выполни задачу **Mxx** из `docs/redesign-migration-plan.md`. Прочитай `AGENTS.md`, `client/ARCH.md`, общие правила и карточку задачи. Проверь её зависимости в `docs/redesign-integration-progress.md`. Реализуй перечисленные шаги, сохраняя соседние рабочие сценарии. Для неописанного небольшого решения используй существующие соглашения проекта; при реальном несовпадении контракта запиши конкретные данные и исправь затронутую карточку. Выполни указанные проверки, обнови статус и журнал. В результате перечисли изменённые файлы, проверенные сценарии, результаты команд и оставшиеся ограничения. Не начинай следующую задачу автоматически.

Журнал создан в M01 и содержит проверенную исходную точку. Если требуется работа нескольких исполнителей одновременно, сначала отдельно распределить файлы и зависимости: по умолчанию этот план рассчитан на последовательную передачу задач и не разрешает параллельные правки общих store/router/API-контрактов.
