## 2. Правила выполнения

1. Перед каждым шагом прочитать актуальные `AGENTS.md`, `server/ARCH.md`,
   затрагиваемый сервис и его тесты. Проверить текущие изменения Git и сохранить
   изменения пользователя.
2. Сохранить классы сервисов и обычные методы экземпляра. Модели, соединение и
   сотрудничающие сервисы использовать через зависимости конструктора.
3. Не менять сигнатуры публичных операций, HTTP-контракты, коды и сообщения
   ошибок, поля результатов, правила валидации и последовательность действий.
4. Сохранить границы транзакций. Вынесенные операции БД получают тот же объект
   `transaction` явно. Не начинать вложенные транзакции в новых методах.
5. Новые пути для очистки фиксировать в публичном методе до файлового действия,
   которое может завершиться ошибкой. Ошибка очистки логируется и не заменяет
   исходное исключение. Файлы PostgreSQL автоматически не откатывает.
6. В изменённых `if` и `else` использовать `{}`. Не совмещать шаг с массовым
   форматированием других методов или файлов.
7. Выделять завершённые этапы операции. Не создавать обёртки над каждой строкой,
   универсальный конструктор запросов, общий `FileService` или новый слой
   репозиториев. Вспомогательные методы остаются в текущем сервисе; небольшие
   чистые функции допустимы рядом с классом согласно `server/ARCH.md`.
8. Не объединять автоматически обработку фото регистрации, профиля и объявления:
   сейчас у них различаются правила, имена файлов и обработка ошибок.
9. Проверять поведение и границы отказов через публичные операции. Не закреплять
   тестами имена вспомогательных методов или число их вызовов.
10. Запускать адресные серверные тесты, указанные для задачи. После завершения
    блока одного сервиса запускать весь набор `node --test server/tests/*.test.js`
    из корня репозитория. `npm test` сервера остаётся заглушкой; фактические тесты
    находятся в `server/tests/` и работают через `node:test`.
11. Для изменённых JS-файлов выполнять `node --check`, для диффа —
    `git diff --check`. Не пересоздавать локальную БД и не запускать миграции или
    seeders: эти задачи не изменяют схему или данные.
12. Показать дифф именно выполненного шага и кратко описать проверки. Следующий
    шаг выполнять после отдельного согласования с пользователем.
