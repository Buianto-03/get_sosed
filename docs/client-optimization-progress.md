### Как повторить браузерный замер

Эти команды запускают профиль и строят таблицы в каталоге `client/` с установленными npm-пакетами.

```sh
node scripts/optimization-profile/run.mjs /tmp/o01.json
node scripts/optimization-profile/report.mjs /tmp/o01.json
```

На macOS скрипт использует системный Google Chrome. Переменная `CHROME_BIN`
задаёт путь к другому исполняемому файлу Chrome. Для сравнения сохранить JSON
каждой ревизии отдельно. Скрипт записывает в него commit, версии, ресурсы,
события и длительности каждого прогона. Для проверки установки достаточно
добавить `TRIALS=1` к первой команде. Таблицы ниже используют пять прогонов.

Стенд создаёт временные сборки и профиль браузера, запускает HTTP и WebSocket
на loopback. Авторизованный синтетический пользователь имеет ID 1, собеседник
открытого диалога — 2, соседнего — 3. В модели объявлений и профилей
используются заглушки фотографий, координаты отсутствуют. Объём ответов
отражает эти fixtures. Данных о размерах ответов действующей установки здесь нет.

| Набор | Объявления | Теги | Избранные | Диалоги | Сообщения в истории выбранного диалога |
| --- | ---: | ---: | ---: | ---: | ---: |
| Малый | 100 | 20 | 50 | 50 | 100 |
| Большой | 1 000 | 200 | 500 | 50 | 5 000 |

Холодное открытие использует новый изолированный контекст. Повторное открытие
загружает тот же URL новым документом в том же контексте. Статика получает
длительный HTTP-кеш, HTML и API — `no-store`. Стенд отдаёт JSON, JS и CSS с gzip,
входящие кадры WebSocket без сжатия. Размер окна — 1440 × 900 CSS px, DPR 1,
искусственные задержки CPU и сети выключены. Локальный тест не воспроизводит
сотовую сеть или производительность БД.

Обычная production-сборка используется для навигаций, ресурсов, LCP и CLS.
Для замеров React в отдельной сборке подключены `react-dom/profiling`, корневой
`Profiler` и точечные счётчики вызовов. Взаимодействия начинаются после
повторного открытия, появления ожидаемых элементов и загрузки шрифтов.
Подтверждение лайка удерживается стендом до регистрации pending. Наблюдаемое
время от события до второго animation frame включает планирование кадров;
отклик на пять букв оценивается по отдельным событиям ввода.

Время рендера — сумма значений `Profiler.actualDuration` за действие. Время
фазы commit получено отдельно через метки React `markCommitStarted/Stopped`.
Интервалы вложенных синхронных commit могут перекрываться. Значения JS heap
сняты после готовности экрана без принудительной сборки мусора.

### Критерии сравнения

Для O09 план требует ноль вызовов строк и ноль обходов истории во время ввода.
Для O08 целевой результат на каждом из двух обновлений — одна карточка, ноль
соседних карточек и ноль обновлений фильтров. Для O03 ввод города или цены
должен давать ноль пересчётов каталога и ноль рендеров группы чекбоксов. Для O10
обновление присутствия или сообщение в соседний чат должно давать ноль
пересчётов и рендеров активной истории. Сравнивать длительности следует при
одинаковом наборе данных и окружении с учётом разброса. Численные бюджеты
времени и объёма предстоит определить в O16.

Число прогонов — 5. Значения показаны как медиана [минимум–максимум]. Стабильные объёмы и счётчики показаны одним числом.

## O09. Ввод в чате

Для выбранного адресата `MessageComposer` хранит черновик, быстрые ответы и
ошибку отправки. Принятая отправка очищает поле и возвращает историю к новым

## O10. События соседнего диалога

Локальным индексом для дедупликации служат ID в уже отсортированной истории.
Для обычного нового сообщения reducer сравнивает его ID с последним и добавляет
в конец. Для запоздалого или переотправленного сообщения позиция определяется
бинарным поиском. Так в Redux хранится одна последовательность объектов сообщений.
Слияние полного снимка истории с поступившими через сокет сообщениями остаётся
отдельной операцией. Вставка в середину массива может сдвигать его элементы.

У строки списка теперь есть только отображаемые поля. Проекция неизменившегося
DTO переиспользуется для того же текущего пользователя. Подготовка открытой
истории зависит от массива сообщений выбранного собеседника. Загрузка
сведений о собеседнике, контекст объявления и открытие/закрытие истории
имеют собственные зависимости и cleanup.

| Действие на большом наборе | Рендеры ConversationRow, O01 → O10 | Проекции истории, O01 → O10 | Суммарный рендер React до, мс | После, мс |

| Ввести пять символов | 250 → 0 (с O09) | 0 → 0 | 14 [11,1–14,8] | 0,9 [0,7–1,2] |
| Получить сообщение в соседнем диалоге | 50 → 1 | 50 → 0 | 4,5 [4,2–4,6] | 0,5 [0,5–0,7] |
| Изменить присутствие соседнего собеседника | 50 → 0 | 50 → 0 | 3,5 [3,3–3,6] | 0 |

## O11. Стоимость загрузки полной истории

В обычной production-сборке получены следующие значения за пять холодных и
пять тёплых открытий каждого набора. WS включает все входящие кадры, включая
присутствие. Длительные задачи зарегистрированы браузерным PerformanceObserver.

| Сообщения | Элементы DOM, из них строки истории | Входящий WS, байт | JS heap при холодном открытии, МиБ | Длительные задачи на одно открытие | Самая долгая задача, мс, холодное / тёплое |
| --- | --- | ---: | --- | --- | --- |
| 100 | 502 / 100 | 32 584 | 4,39 [4,21–4,61] | 0 | — |
| 5 000 | 5 402 / 5 000 | 1 637 986 | 11,29 [8,53–11,55] | 1 | 85 [84–89] / 87 [85–87] |

До O11 пара `INITIALIZE → SET_MESSAGES` передавала всю историю собеседника
одним ответом. Даже при тёплом кеше открытие большого диалога передавало 1,64 МБ
и блокировало основной поток дольше 80 мс.

### Реализация

Клиент использует `GET_HISTORY_PAGE → HISTORY_PAGE`. Старые клиенты продолжают
получать историю через `INITIALIZE → SET_MESSAGES`.
Запрос содержит `requestId`, `receiverId`, `limit` (по умолчанию 50, максимум 100)
и один необязательный курсор. Без курсора сервер отдаёт последние сообщения.
`beforeId` запрашивает предыдущую страницу с меньшими ID, `afterId` — следующие
ID при восстановлении связи. Для уже открытого пустого диалога используется
`afterId: 0`. Все границы исключающие. Сервис читает оба направления только
для авторизованного пользователя и проверенного адресата. Выборка ограничена
`limit + 1` строками, клиент получает до `limit` сообщений в порядке возрастания
ID. Ответ указывает `hasMore` и `nextCursor`. Успех и ошибка связаны с запросом
через `requestId` и `receiverId`. При совместном выпуске сначала обновляется
сервер. [Описание WebSocket-контракта](../server/docs/README.md)

При догрузке вверх клиент сохраняет видимое сообщение и его смещение. При
разрыве связи фиксирует границу и продвигает курсор восстановления только по
ответам страниц. Live-события объединяются с историей по ID. Ответы закрытого
диалога и прежней сессии отбрасываются. При уходе из диалога загруженная история
освобождается. Восстановление охватывает доступные серверу сообщения выше
сохранённого ID. Курсор по ID не подтверждает доставку сообщения.

### Реализация и владельцы

Сервисы чтения объявлений, каталога, страниц своих объявлений, избранного,
списка диалогов, summary и заинтересованных принимают ReadOptions с
необязательным AbortSignal. Thunks передают thunkAPI.signal до Axios;
ошибки чтения сохраняют исходный тип, включая отмену.

- SearchRoute отменяет предыдущий поиск при изменении URL и retry;
  cleanup отменяет текущий, включая запрос последнего retry.
- ListingRoute отменяет детали и заинтересованных при смене ID и unmount;
  заинтересованные также перезагружаются при смене владельца сессии.
- HomeRoute, useTagCatalog, summary и контекст объявления чата имеют
  локальные контроллеры; retry, смена ключей и unmount отменяют старую загрузку.
- MessagesRoute владеет отменой списка диалогов при retry, смене пользователя
  и unmount; смена собеседника не перезагружает общий список.
- useMyAdverts отменяет первую страницу и догрузки предыдущего владельца
  или generation. Ошибка/отмена догрузки сохраняет уже показанные карточки.
- Общая загрузка избранного принадлежит session listener: UI retry и вход
  используют savedLoadRequested, listener хранит abort handle и отменяет его
  при смене пользователя. Уход с одного экрана не отменяет общий список.

requestId, generation, active и проверки ownerId сохранены как дополнительная
защита от поздних ответов. Отмена завершает loading без Error/NotFound,
сохраняет подтверждённый результат. Для деталей и заинтересованных того же ID
pending не уничтожает последнюю подтверждённую запись. initialized в избранном
позволяет вернуть Ready после отмены reload даже при успешном пустом списке.

HTTP interceptor не начинает refresh для отменённого запроса и не повторяет
его после refresh. Отмена во время ожидания немедленно отклоняет только
промис этого потребителя. Общий refresh остаётся активным для остальных;
реальная ошибка refresh вызывает onUnauthorized один раз на общую операцию.
Отмена потребителя не вызывает onUnauthorized. Формы и мутации не получили
автоматической отмены. Кеш каталога относится к следующей O05 и не добавлялся.

## O05. Общий кеш каталога тегов

Выполнена 22 ноября 2026 года в ветке frontend/refactor. Исходная ревизия —
`fe9cf9e23394bac688551e0748c0494647fd09d8`, включая переименование

не добавлялись.

### Реализация и политика кеша

В entities/advert добавлены tagCatalogModel, tagCatalogThunk,
tagCatalogSlice и tagCatalogSelectors. useTagCatalog подписывается на общий
Redux-кеш и сохраняет прежний UI-контракт tags/state/error/reload.
Существующие поиск, публикация и preview не получили новых props;
preview по-прежнему может использовать переданный каталог без Redux.

Ключ — origin настроенного API, данные — весь публичный каталог при query=''.
В кеше только теги и сериализуемые метаданные; частные данные сессии,
профиля и избранного не переносятся. Смена пользователя не сбрасывает
публичный каталог. Кеш живёт в памяти текущего store и не сохраняется
между перезагрузками документа или вкладками.

TTL — исходные пять минут из плана, отсчитываемые после успешной проверки
ответа. Новое подключение использует свежую запись, после TTL запускает
загрузку. Фонового polling и автоматического таймера нет. reload обходит TTL,
но во время pending присоединяется к текущей операции. Синхронный condition
по requestId объединяет одновременные запросы, включая StrictMode replay.
O01/O05 подтверждают стоимость повторных загрузок, но не измеряют частоту
изменений серверного каталога; оснований менять исходный TTL не появилось.

Размонтирование потребителя больше не отменяет общую загрузку. Даже после
ухода последнего потребителя публичный ответ заполняет кеш. Явная отмена
cache thunk сохраняет последний успешный массив и fetchedAt, снимает loading
без Error и помечает запись несвежей; поздний ответ не проходит requestId.
Сетевой отказ или невалидный каталог не заменяют последние успешные теги
и timestamp, показывают ошибку/retry и разрешают немедленный повтор.
Это заменяет локальную политику useTagCatalog из исторического раздела O04.

Черновики остаются в компонентах форм, выбранные ID — в URL/черновике;
обновления, ошибки и retry кеша их не очищают. Неизвестный ID сохраняется
с подписью #ID, а после появления в каталоге получает реальную подпись.
При ошибке проверяются прежние состояния доступности: поля и выбранные
значения сохранены, условия отключены до успешного retry.
