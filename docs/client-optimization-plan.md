# План оптимизации клиентской части GETSOSED

Дата: 20 октября 2026 года. Статус: план подготовлен, реализация не начата.

Цель — уменьшить начальную загрузку, объём запросов и работу при взаимодействии
с интерфейсом, одновременно упростить чтение кода и закрепить границы модулей.
Изменения выполняются небольшими задачами с отдельной проверкой результата.

План основан на аудите рабочего клиента и анализе production-сборки. Он дополняет
[план редизайна](redesign-migration-plan.md) и
[журнал интеграции](redesign-integration-progress.md), а не заменяет их приёмку.
Архитектурные ограничения заданы в [AGENTS.md](../AGENTS.md),
[client/ARCH.md](../client/ARCH.md) и [server/ARCH.md](../server/ARCH.md).

## 1. Исходная точка и границы

### Что подтверждено аудитом

| Область | Наблюдение | Следствие |
| --- | --- | --- |
| Начальная загрузка | Основной JS около 644 КБ, gzip около 209 КБ. В пробной сборке без корневого ChakraProvider — около 379/121 КБ | У провайдера и его зависимостей есть измеримая стоимость; удаление ещё не проверено визуально |
| Статические ресурсы | `mainPhoto.jpg`: 1 481 435 байт, 1920 × 1080; `Inter-Variable.ttf`: 876 576 байт | Одинаковые тяжёлые ресурсы используются и на телефоне |
| Поиск | Ответ содержит весь массив, UI показывает `slice(0, visitableCards)` | Трафик, валидация и память растут со всей выдачей |
| Главная | `getAdverts()` получает все объявления, helper сортирует их и оставляет три | Для маленькой подборки загружается лишняя коллекция |
| Чат | Состояние ввода находится в ChatPage; страница отображает всю историю | При вводе повторяется работа над списками |
| Каталог тегов | `getPrimaryTags` вызывается внутри прохода по тегам; подписи тоже вычисляются повторными поисками | Форма повторяет вычисления даже при изменении несвязанного текстового поля |
| Запросы | Есть защита от поздних ответов через requestId/active/generation, но нет передачи AbortSignal | Ненужные запросы продолжают выполняться |
| Структура | Сосуществуют старый UI, новые экраны и временно разделённые `entities/advert` и `entities/listing` | Нужна управляемая очистка после подтверждения переноса поведения |

Размеры относятся к аудиту 20 октября, указаны в десятичных единицах и требуют
повторной фиксации в O01. Они не являются замерами скорости на устройстве.
Браузерные задержки, LCP, CLS, память и сетевые объёмы реальных коллекций ещё
не измерены. Пробная сборка без ChakraProvider не означает готовность его удаления.

### Что уже работает и должно сохраниться

- Маршруты загружаются через React.lazy; роутер создаётся один раз.
- Применённые фильтры живут в URL, черновик формы — локально. Ввод до применения
  не запускает поиск. Back/Forward восстанавливают фильтры.
- Поиск и детали имеют независимые состояния; поздний ответ не заменяет актуальный.
- Избранное имеет единый источник состояния, pending/error по ID и защиту от
  повторной мутации. Данные прежнего пользователя не попадают в новую сессию.
- Refresh выполняется одним общим запросом при одновременных отказах авторизации.
- На сессию приходится одно WebSocket-соединение с восстановлением после разрыва.
- Собственные объявления уже загружаются порциями через `/adverts/mine`.
  Этот API служит образцом, повторно реализовывать его не нужно.
- CreateListingButton остаётся компонентом на основе общего Button с useNavigate
  внутри. Навигационный callback из родителя не возвращается.

### Ограничения изменений

1. Сначала получить измерения, затем сравнивать изменения в одинаковых условиях.
   Наличие map, inline callback или нового объекта само по себе не считается дефектом.
2. Не вводить массово memo/useMemo/useCallback. Для мемоизации нужны конкретная
   стоимость, стабильные зависимости и подтверждённый результат.
3. Не совмещать этот план с переходом на другой state manager, RTK Query,
   обновлением всех библиотек или переименованием всех доменных терминов.
4. Удаление старого UI, ChakraProvider и пакетов выполняется в рамках Q03 после
   Q01/Q02. Не дублировать их приёмку отдельной формальной отметкой.
5. Чистые преобразования принадлежат helper.ts своего компонента или слайса;
   orchestration запросов — route hook/thunk; представления получают данные и действия.
   Селекторы entities не импортируют UI-модели из pages.
6. Сохранить направление FSD и единственное существующее исключение для
   `app/store/hooks`. Общий код выносить вниз только при общей ответственности.
7. API- и WebSocket-изменения выделять явно. До их готовности не подменять
   серверную пагинацию клиентским slice или демонстрационными данными.

### O04. Отменять ненужные HTTP-загрузки

**Файлы:** advertService, chatListService, entity thunks, SearchRoute, HomeRoute,
ListingRoute, MessagesRoute, useMyAdverts, `shared/api/client.ts`.

1. Провести AbortSignal от владельца загрузки через thunkAPI.signal/options
   сервиса до Axios. Отменять предыдущий поиск при смене фильтров и локальные
   загрузки при смене ID/размонтировании.
2. Различать отмену, сетевой отказ и предметные ошибки. Отмена не показывает
   Error/NotFound, не очищает сессию и не уничтожает сохранённый результат.
   Состояния загрузки отменённого запроса должны завершаться корректно.
3. Сохранить requestId, generation и проверку владельца как защиту от гонок.
   Не распространять политику отмены чтения автоматически на отправку форм и мутации.
4. Проверить interceptor: отменённый запрос не повторяется после refresh;
   отмена одного потребителя не отменяет общий refresh остальных запросов.

**Проверки:** быстро сменить фильтры/ID, уйти со страницы, выполнить retry,
сменить пользователя; одновременно воспроизвести refresh и отмену одного запроса.

**Готово, когда:** ненужные загрузки отменяются на клиенте, актуальные данные
сохраняются и ошибки отмены не видны пользователю. Отмена HTTP на клиенте
не объявляется гарантией остановки уже начатого SQL-запроса на сервере.

### O05. Разделить загрузку и потребление каталога тегов

**Файлы:** `entities/advert/model/use-tag-catalog.ts`, модель/селекторы каталога,
advertService, поиск и публикация.

1. Разместить общий кеш публичного каталога в owning entity, используя текущий
   Redux-подход. Если добавляется Redux-модуль, разделить tagCatalogModel,
   tagCatalogThunk, tagCatalogSlice и tagCatalogSelectors.
2. Задать политику: ключ — полный публичный каталог для текущего API origin;
   исходный TTL — пять минут, явный reload обходит TTL. Порог уточняется по O01.
3. Объединять одинаковые параллельные загрузки. Ошибку/отменённый ответ не считать
   свежим кешем; сохранять последний успешный каталог и показывать доступный retry.
4. Unmount одного подписчика не должен отменять запрос, нужный другому. Отменой
   общей загрузки управляет владелец кеша. Не переносить в этот кеш частные данные.
5. Черновики и неизвестные tag IDs сохраняются при обновлении или ошибке каталога.
   Preview продолжает передавать собственные данные через прежний UI-контракт.

**Готово, когда:** переход поиск → публикация в пределах TTL не вызывает повторный
запрос, два потребителя делят одну загрузку, reload/retry работают предсказуемо.

### O06. Согласовать и реализовать ограниченные API коллекций

**Зависимость от сервера:** явная. Изменения сервера выполняются отдельной задачей
с соблюдением server/ARCH.md; клиентские потребители переводятся в O07.

**Область:** AdvertService/Controller/router сервера, advertService/Zod клиента,
контракт поиска и свежей подборки.

1. Для текущего POST `/adverts/filters` согласовать pagination request и ответ
   `{ items, total, page, limit }`, используя существующий `/adverts/mine` как образец.
   Определить limit/default/max, валидацию и безопасный offset.
2. Определить явный контракт свежей подборки, например GET `/adverts/fresh?limit=3`.
   Это предлагаемый новый маршрут, сейчас его наличие не предполагается.
3. Установить порядок `createdAt DESC, id DESC`; поиск и выдача следующей страницы
   используют один и тот же порядок. Не менять текущую семантику фильтров и ALL-match тегов.
4. Считать total по объявлениям, не по строкам join. Сохранить фотографии,
   порядок фото, nullable-поля и нужные данные автора в ответе.
5. Указать политику изменения данных между страницами: offset-pagination не
   гарантирует снимок базы; клиент убирает повторы по ID, новая выдача начинает
   загрузку заново. При необходимости строгого снимка нужен отдельный cursor-контракт.
6. Обновить контракт и server/ARCH.md. Не поддерживать две неявные формы ответа
   в одном сервисе. API и потребители выпускаются согласованно.

**Проверки:** пустая/последняя страница, одинаковые даты, несколько тегов и фото,
невалидная пагинация, count без дублирования, ограничение rows на уровне запроса.

**Готово, когда:** API возвращает ограниченное число объявлений и корректный total,
контракт подтверждён адресной API/БД-проверкой. Серверный placeholder npm test
не используется как доказательство работоспособности.

### O07. Загружать в поиске и на главной только нужную подборку

2. «Показать ещё» загружает следующую страницу, блокирует параллельные запросы
   и сохраняет карточки при ошибке. Retry повторяет ту же неуспешную страницу.
3. При новых фильтрах сбросить страницу и отменить прежний запрос. Поздняя
   догрузка старого фильтра не добавляется в новую выдачу. Объединять карточки по ID;

**Готово, когда:** первая выдача содержит только одну страницу, догрузка вызывает
новый ограниченный запрос, главная получает не больше трёх объявлений;

## 4. Проверки и приёмка

Для реализации каждой затронутой клиентской задачи выполнить в `client/`:

```sh
npm test
npm run lint
npm run build
```

Дополнительно нужны проверки изменённого поведения, а не тесты, повторяющие
реализацию. После успешных проверок повторять их без новых изменений/оснований
не требуется. Для изменения только Markdown проверить ссылки и согласованность;
это не основание запускать весь клиентский набор.

| Изменение | Обязательная адресная проверка |
| --- | --- |
| Медиа/provider/CSS | Первый экран и прокрутка; 1440/1024/768/390 px, переполнение на 320 px; кириллица, фокус, overlays; холодная загрузка |
| Поиск/API | Фильтры URL, Back/Forward, total, пустая/последняя страница, повторные клики, retry догрузки, смена фильтра во время ответа |
| Кеш/отмена | Два потребителя, TTL/reload, unmount одного, поздний ответ, retry, отсутствие пользовательской ошибки отмены, общий refresh |
| Избранное | Общий saved на разных экранах, pending по ID, ошибка мутации, две учётные записи, поздний ответ прежней сессии |
| Чат | Ввод и draft, две учётные записи, первый диалог, повтор/перестановка событий, поздняя history, reconnect, смена адресата |
| Пагинация истории | Cursor/hasMore, отсутствие дублей/пропусков, scroll anchor, длинный текст, клавиатура и восстановление после разрыва |
| Архитектура | FSD, imports/exports, разделение Redux-файлов, production/preview graph, независимость entity от pages и соседних entities |

Для задач API/WS выполнить адресные проверки сервера и тестовой БД с сохранением
текущих данных. Сброс БД не является обязательным этапом оптимизации. Секреты и
пользовательские данные не включаются в отчёты и тестовые fixtures.

## 5. Как выполнять и фиксировать задачи

1. Брать одну карточку, проверять её зависимости и актуальное состояние исходников.
   Перед правками фиксировать существующие изменения; чужую работу не перезаписывать.
2. Если исходное предположение уже не соответствует коду, обновить конкретную
   карточку и основание решения. Не реализовывать устаревшее требование буквально.
3. Вносить ограниченный набор изменений с понятной ответственностью. Задачи,
   меняющие API и потребителя, координировать как один совместимый выпуск.
4. В журнал записывать: ID/статус, изменённые файлы/контракт, проверки и результаты,
   сравнение до/после, оставшиеся ограничения. Не использовать число тестов
   или строк кода как критерий архитектурного качества.
5. Для параллельной работы заранее разделять файлы. Store, router, entity contracts,
   API и протокол нельзя независимо переписывать нескольким исполнителям.

План считается выполненным после приёмки обязательных O01–O10 и O12–O16,
согласованного решения по O11 и фиксации фактического результата Q03.
Наличие плана само по себе не меняет статус задач редизайна.
